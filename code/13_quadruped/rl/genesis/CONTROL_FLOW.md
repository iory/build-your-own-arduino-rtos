# ロボット制御の流れ (Genesis 版 NN 学習 → 実機)

根拠は次のファイルです。`rl/genesis/gs_env.py`、`rl/cpu/task.py`(定数)、`include/quad_control.h`、`include/arduino_quad_policy.h`、`src/main.cpp`。

## 1. 全体像

```
学習 (Genesis, GPU)                       実機 (Arduino, 50 Hz)
  PPO ──> actor MLP 87→96→64→8  ──export──>  quad_policy_forward()
  (task.py の MDP を gs_env.py が再現)        (quad_step, main.cpp のループ)
```

- 制御周期は **20 ms (50 Hz)** です。`STEP_DT = PHYSICS_DT(5 ms) × DECIMATION(4)`。
- 物理は 5 ms (200 Hz) で進み、ポリシーは 4 物理ステップに 1 回だけ呼ばれます。
- 学習した方策は実機でも同じ観測・同じ式で動きます。sim2sim は MuJoCo で検証します。

## 2. 入力 (Actor 観測)

`ACTOR_TERMS = command, phase, joint_pos, joint_vel, actions`。これを **履歴 3 ステップ** 分並べます。

| 項 | 次元 | 中身 | 学習時のノイズ |
|---|---|---|---|
| `command` | 3 | 速度指令 `[vx, vy=0, wz]` | なし |
| `phase` | 2 | `sin, cos(2π·(t mod 0.32 s)/0.32 s)`。`‖cmd‖<0.1` なら 0 | なし |
| `joint_pos` | 8 | `q − DEFAULT_JOINT_POS` [rad] | ±0.02 |
| `joint_vel` | 8 | 関節角速度 [rad/s] | ±0.3 |
| `actions` | 8 | 前回の方策出力 | なし |
| 小計 | **29** | | |
| × 履歴 3 | **87** | 各項ごとに古い順に連結 (`QUAD_OBS_DIM=87`) | |

- IMU、基体速度、足接触は Actor には入りません。
- 基体速度や足の高さ、接触力などは Critic 専用の特権情報で、学習にだけ使います。
- 履歴バッファは、エピソード開始時に最初の 1 サンプルを全スロットへ複製して埋めます (`_need_backfill`、`quad__push`)。

## 3. 計算

### 3.1 方策ネットワーク
```
x = (obs − obs_mean) / obs_std          # obs_normalization
h1 = ELU(W1 x  + b1)   # 87 → 96
h2 = ELU(W2 h1 + b2)   # 96 → 64
a  =      W3 h2 + b3   # 64 → 8   (出力は活性化なし)
```

- 学習時は `a` がガウス分布の平均で、`init_std=1.0` の標準偏差が付きます。
- 実機では平均 `a` を決定論的に使います。`QUAD_ACTION_CLIP=0` なのでクリップはありません。

### 3.2 行動 → 目標関節角
```
target = DEFAULT_JOINT_POS + 0.25 · a          (ACTION_SCALE = 0.25 rad)
```
- 学習時だけ、これに `− encoder_bias` (ドメインランダム化のエンコーダ零点ずれ) が付きます。

### 3.3 サーボ側 (制御ではなく物理)
- 位置 PD: `KP=25, KD=0.5`。
- 逆起電力ダンピング: 0.624。
- トルク上限: `STALL_TORQUE`。
- 学習時はこれらを `×0.6–1.6`、`×0.4–2.0`、`×0.7–1.0` などで乱数化します。

## 4. 出力

- **8 関節の目標角 [rad]** です。FL / RL / RR / FR の各脚に hip と knee があります。
- 実機では `servo_bus_write(g_target)` でサーボ (STS3215 / RCB-4) に送り、サーボ内蔵の位置制御が追従します。
- トルクは NN が直接出すのではなく、PD が目標角から生成します。

## 5. タイムサイクル (1 制御ステップ = 20 ms)

### 5.1 学習時 (`GenesisQuadEnv.step`)

```
step 開始 (時刻 t)
 ① 観測 o_t = 前ステップ末の状態 (_read_state → _observe)
 ② a_t = π(o_t)                      ← ここで推論 (シミュレータ内では 0 ms)
 ③ prev_action ← action; action ← a_t
    target_t = home + 0.25·a_t − bias
 ④ 物理 4 サブステップ (各 5 ms):
      delay line に target_t を push
      lag ∈ {4,5,6,7} を一様乱数で選び (毎サブステップ)、lag サブステップ前の target を読む
      PD で駆動して 1 物理ステップ進める
 ⑤ 状態読み出し → 終了判定 → 報酬 → リセット → 指令再サンプル → 押し外乱 → 観測
```

### 5.2 実機 (`main.cpp` の loop)

```
每 20 ms (next_us で締切管理):
  servo_bus_read(q)                         # 関節角 (最新値)
  qd = 0.6·qd_prev + 0.4·(q − q_prev)/dt    # 差分 + 一次 LPF (dt は実経過時間)
  quad_step():
      履歴リングに (cmd, phase, q−home, qd, last_act) を push
      87 次元を組み立て → MLP → target = home + 0.25·a
      last_act ← a
  servo_bus_write(target)
```

- 実機には `ang_vel` / `gravity` を入れる `_imu` 版もあります。ただし Genesis で学習している Walk の Actor には IMU は入りません。
- 周期を落としたときは、遅れを詰め直さずに `g_step += lost` で歩容クロックを実時間に合わせます。

## 6. 何フレーム前のデータを使うか

| 項目 | 時刻 | 備考 |
|---|---|---|
| 現在の観測 (`joint_pos`, `joint_vel`, `command`) | **t** (その制御ステップ開始時点の最新計測) | 0 フレーム遅れ |
| 履歴 | t, t−1, t−2 フレーム (= 0, 20, 40 ms 前) | 履歴 3 |
| `actions` 項 | a_{t−1}, a_{t−2}, a_{t−3} | 自分が直前に出した出力 |
| `phase` | `step_i × 20 ms` から計算 | 実時間に同期 |
| 速度 `joint_vel` | 実機では差分なので約 20 ms 窓、LPF で更に平滑 | 学習時の真値速度とは性質が違う |

## 7. レイテンシ

### 7.1 学習時にモデル化している遅れ (遅延ライン)
- 遅延は **4〜7 物理ステップ = 20〜35 ms、平均 27.5 ms** です。サブステップごとに一様乱数で再抽出します。
- 目標 `target_t` は 4 サブステップの間同じ値を push し続けるので、ちょうど 1 制御周期分前の値から効き始めます。
- つまり **観測 (t) → 行動 a_t → サーボに効き始める**までは最短 1 フレーム (20 ms)、最長で約 35 ms です。
- 1 フレーム未満の遅れはありません。現在の行動がそのステップ内で効くことはない設計です。

### 7.2 実機の遅れ (実測) と学習側の遅延の関係

**学習側の遅延は、実機の実測に合わせた値です** (`rl/robot_cfg.py:159-175`)。実機に遅延が無いわけでも、学習側が保守的に盛っているわけでもありません。

| 項目 | 実測 |
|---|---|
| バス往復 | 約 0.2 ms |
| 推論 | 約 3.6 ms |
| **STS3215 サーボ内部のデッドタイム** (指令処理とモーションプロファイル) | **約 23 ms** |
| 合計 | **約 27 ms = 5.4 物理ステップ = 1.35 制御周期** |

- 2 関節で独立に同定しました。FL_hip は 26.7 ms、FL_knee は 28.8 ms です。4〜7 ステップ (20〜35 ms) はこの 2 値を含みます。
- 以前は 1〜4 ステップ (5〜20 ms) でした。「バス往復 + 推論」だけを見積もり、サーボ内部の約 23 ms が欠けていたためです (推測の誤りではなく項目の欠落)。
- 位置 PD の `stiffness=25` も遅延を入れて同定しています。遅延を入れないと、無駄時間をゲインの低下で説明してしまい、低く出ます。
- ループ実測は `loop avg` が **学習方策 (rl) で約 5.8 ms、保持中で約 2.4 ms** です (`README.md`)。予算は 20 ms で、`late` / `skipped` で超過を監視します。

**意図**

- 実機の遅れは計算よりサーボ内部が支配的です。「現在のステップ内には効かず、1 周期以上古い指令でサーボが動く」状況をシミュレータで再現する必要があります。
- 遅延を 4〜7 の範囲で毎物理ステップ乱数化するのは、実測のばらつきを吸収し、方策が特定の遅れ値に過適合しないようにするためです。
- `rl/README.md` でも、`delay_min/max_lag` (27 ms の指令遅れ) は sim2real の要として、mjlab 1.2.0 に合わせて外すことはできないとされています。

### 7.3 まとめ
```
計測(t) → [バス 0.2 + 推論 3.6 ms] → サーボ指令 → [サーボ内部デッドタイム ≈ 23 ms] → 動き出す
         └───────────── 合計 ≈ 27 ms (学習側の遅延ライン 20–35 ms と対応) ─────────────┘
次の観測は 20 ms 後、履歴は 40 ms 前まで
```

### 7.4 入力フレームと出力が効く区間

時刻 0 を「いま推論する瞬間」、単位を制御フレーム (20 ms) とします。

**入力**

- 物理情報 (`joint_pos`, `joint_vel`, `command`, `phase`) は、フレーム **−2, −1, 0** の 3 点です。
- 制御情報 (`actions`) は **a₋₃, a₋₂, a₋₁** です。a₀ はまだ存在しないので含まれません (範囲は [−3, −1])。

**出力 a₀ が効く区間**

- a₀ は **[0, 1] の間に出力 (送信) されます**。シミュレータでは、その 4 サブステップで遅延ラインに push し続けます。
- 効くのは、早くてもフレーム 1 から (lag=4) です。lag=7 なら [1, 2] の後半から [2, 3] の前半にずれ込みます。

| 区間 | その区間で PD が追う目標 (シミュレータ) |
|---|---|
| [0, 1] | a₋₁ が主で、lag 5〜7 のときは前半に a₋₂ が混ざる |
| [1, 2] | a₀ が主で、lag 7 のときは前半だけ a₋₁ |
| [2, 3] | lag 5〜7 のときは前半に a₀ が残り、その後は a₁ |

```
入力: 物理 [-2, -1, 0]  +  過去の行動 [-3, -2, -1]
出力: a₀ を [0,1] で送信 → 主に [1, 2] の関節目標になる (約 20–35 ms 後から)
```

**方策は遅れを知らない**

- 方策は毎フレーム目標を出すだけで、それが何 ms 後に効くかを明示的には知りません。
- 遅れは、学習時は遅延ラインが、実機はサーボ内部が作ります。
- 方策は、約 27 ms の遅れを前提に報酬が最大になるよう学習され、遅れを織り込んだ先読みをするようになります。

## 8. 補足

- **sim と実機の対応**: `actions` 項は、sim では更新後の `self.action` (= a_t) が次ステップの観測に入ります。実機では `s->last_act` を push してから推論するので、同じ a_t が次ステップに入り、両者は整合します。
- **sim と実機の速度の違い**: `joint_vel` は sim では真値、実機では差分 + LPF (0.6/0.4) です。学習時に ±0.3 のノイズで吸収しています。
- **推論時間**: `rl/robot_cfg.py` のコメントによると、実測は推論約 3.6 ms、バス約 0.2 ms です。`loop avg` はこれに加えて IMU 更新などを含みます。
