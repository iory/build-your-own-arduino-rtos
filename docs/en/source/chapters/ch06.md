# Chapter 6: Memory Protection

:::{admonition} What this chapter answers: why does the OS survive when an app crashes?
:class: tip

On a PC, when one app crashes, the OS and the other apps keep running.
The OS ends only the program that misbehaved.

In this chapter the OS catches the exceptions (faults) the CPU raises on a
division by zero or a write to an address that does not exist, and stops only
the task that caused it. The other tasks carry on as if nothing happened.
:::

### 1. Crash five times in a row

Send `d` five times in a row, wait a little, then list the tasks with `p`.

**Predict:** how many times does `FAULT DETECTED` appear?

:::{dropdown} Answer
**Only four times.** The fifth `d` still prints `Creating div-by-zero crash task...`,
but the `[Crash] Dividing by zero in 3 seconds...` line that should follow never appears.

```text
Creating div-by-zero crash task...
[Crash] Dividing by zero in 3 seconds...
Creating div-by-zero crash task...
[Crash] Dividing by zero in 3 seconds...
[Heartbeat] 1
Creating div-by-zero crash task...
[Crash] Dividing by zero in 3 seconds...
Creating div-by-zero crash task...
[Crash] Dividing by zero in 3 seconds...
Creating div-by-zero crash task...
[Heartbeat] 2
(FAULT DETECTED four times)

ID  NAME           STATE
0   idle     READY
1   LED     BLOCKED
2   Heartbeat     BLOCKED
3   Shell     RUNNING
4   Crash_Div     TERMINATED
5   Crash_Div     TERMINATED
6   Crash_Div     TERMINATED
7   Crash_Div     TERMINATED
```

The task table `g_tasks` has room for only `MAX_TASKS` = 8 entries. The four
created at boot (idle, LED, Heartbeat, Shell) use half, and `Crash_Div` fills
the other four. A `TERMINATED` task's slot is never reused, so the fifth
`os_create_task()` returns -1 and does nothing. The shell does not check that
return value, so it announces the new task and never notices the failure.

Each finished task permanently uses up a slot, so this OS is not suited to
recreating crashed tasks over and over.
:::

### 2. Turn off the divide-by-zero trap

In `fault_init()` in `src/os_fault.cpp`, comment out the setting that makes a
division by zero raise an exception.

```diff
-    SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;
+    // SCB->CCR |= SCB_CCR_DIV_0_TRP_Msk;
```

**Predict:** when you send `d`, what does `100 / 0` do?

:::{dropdown} Answer
**`FAULT DETECTED` never appears.** Yet `p` shows `Crash_Div` as `TERMINATED`.

```text
Creating div-by-zero crash task...
[Crash] Dividing by zero in 3 seconds...
[Heartbeat] 1
[Heartbeat] 2
[Heartbeat] 3

ID  NAME           STATE
0   idle     READY
1   LED     BLOCKED
2   Heartbeat     BLOCKED
3   Shell     RUNNING
4   Crash_Div     TERMINATED
```

Without this setting (`CCR.DIV_0_TRP`), the Cortex-M divide instruction does not
raise an exception on division by zero; it returns 0 and carries on
([Arm's "Divide and Conquer"](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/divide-and-conquer)).
`c` stays 0, `task_crash_divzero()` runs to the end and returns, and
`task_exit()`, which catches returning tasks, marks it `TERMINATED`.

So the program carries on with a wrong answer and no error.
That is why `fault_init()` turns this setting on.
:::
